# Retail-profile simulation check — fixed before model calls

September7,2026. This is an additional simulated-profile transfer check, not a real inventory/revision benchmark. Source: official FreshRetailNet-50K, CC BY4.0, revision08c1fab7f9257bc73679d415d65d644165d351d4. Source values, extraction hashes and selection are in external_data.md and data/freshretail_manifest.json.

A deterministic identifier hash separates64store-product windows into16development and48heldout stores. This is source separation, not proof of statistical independence across stores. All-zero profiles are retained. The initial72hours form36two-hour historical sales bins; the next24hours form12future bins. Remaining72hours are not used. Past-only normalization maps bins to integers by half-up rounding of10×bin_sum/max_past_bin_sum, with denominator1when the past maximum is0. Future values do not fit the normalizer, and no cap is applied. These are normalized observed sales, possibly censored by stockouts, used as scenario proxies rather than true demand.

The inventory process, receipt policy, report delays, and corrections are synthetic. Thirty-six receipt events alternate with36historical demand events; six receipts interleave with12future demand events. Initial stock12. Historical receipt budget is half-up(3S/4) and future receipt budget half-up(S/6), where S is total quantized PAST demand. Seeded positive integer weights and largest-remainder allocation assign these exact budgets to receipt slots. No future quantities or oracle stock fit the receipt policy. Late reports and corrections are generated explicitly. As in the primary study, snapshots refer to reconstructed state under report visibility, not actual retailer inventory.

Development-only ground-truth check: among16stores,8have historical loss,12have future loss, and12end with positive inventory. These descriptive checks address degeneracy and did not select individual stores or model outcomes.

Model development check: first4development stores,4configurations×3arms×1rep=48requests. If semantics/transport pass,48heldout stores×4configurations×3arms×2reps=1152requests. Same v2 model configurations, request rules, outputs and scoring as primary. Store/window is the paired bootstrap unit; repetitions are averaged. Source profiles differ from primary generated trajectories, but reporting anomalies remain simulated. Report all48stores and all configurations, with source and transformation attribution in the manuscript and artifact.
